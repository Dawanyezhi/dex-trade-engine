# 08-production-architecture: 学习目标与自检问题

## 知识点分层

### L1 -- 基础概念（必须掌握）

- 限流的基本目的：保护下游系统不被过量请求压垮
- 令牌桶算法的工作原理：桶容量、填充速率、消费令牌
- 令牌桶 vs 漏桶 vs 滑动窗口的区别
- Worker 池的作用：限制并发 goroutine 数量，避免资源耗尽
- Go 中 `chan struct{}` 作为信号量的用法
- `sync.Mutex` 和 `sync.RWMutex` 的适用场景
- 监控的三大支柱：指标（Metrics）、日志（Logs）、追踪（Traces）
- 告警分级：Info / Warning / Critical 的语义

### L2 -- 核心实现（需要理解原理）

- 令牌桶的实现细节
  - 惰性填充（lazy refill）：不用定时器，而是在每次请求时计算经过的时间并补充令牌
  - `Allow()` 非阻塞 vs `Wait(ctx)` 阻塞等待的选择
  - 并发安全：为什么用 `sync.Mutex` 而不是 `sync/atomic`（多个字段需要原子更新）
- Worker 池的实现
  - 信号量模式：`sem <- struct{}{}` 获取许可，`<-sem` 释放许可
  - 为什么用 `chan struct{}` 而不是 `chan bool`（零内存开销）
  - 与 `sync.WaitGroup` 的配合使用
- 多链配置的设计
  - `ChainConfig`（静态配置）vs `ChainRuntime`（运行时配置）的分离
  - 热更新的并发安全：`sync.RWMutex` 保护读多写少的场景
  - 灰度发布：按百分比控制流量到新 DEX
- 监控服务的设计
  - 定时检查 vs 事件驱动的取舍
  - 指标聚合：原子计数器（`sync/atomic`）的高效使用
  - 告警触发条件：阈值设计（如报价失败率 > 50%）

### L3 -- 进阶设计（生产中需要）

- 分布式限流
  - 单机令牌桶在多实例部署时失效：每个实例独立限流，总 TPS 是实例数的倍数
  - Redis + Lua 脚本实现分布式令牌桶
  - 限流粒度：全局限流 vs 按链限流 vs 按 DEX 限流 vs 按用户限流
- 背压与降级策略
  - 有界队列 + 拒绝策略（丢弃最旧/丢弃最新/阻塞等待）
  - 优先级队列：紧急交易优先处理
  - 熔断器模式（Circuit Breaker）：当下游持续失败时自动熔断，定期探测恢复
- 配置中心集成
  - Apollo/Nacos 的推拉模型
  - 配置版本管理：每次变更都有版本号，支持回滚
  - 配置变更审计：谁在什么时间改了什么配置
- 可观测性体系
  - Prometheus 指标设计：Counter / Gauge / Histogram / Summary
  - 结构化日志与日志聚合（ELK / Loki）
  - 分布式追踪：一笔 Swap 从请求到链上确认的完整链路

### L4 -- 架构视角（通盘理解）

- 限流在整体架构中的位置
  - API 网关层限流（保护入口）
  - 服务间限流（保护下游）
  - RPC 客户端限流（保护节点）
  - 三层限流的协调：避免重复限流导致实际吞吐远低于预期
- 多链架构的可扩展性
  - 新增一条 EVM 链的完整流程：配置 -> 注册 -> 灰度 -> 全量
  - 跨链一致性：所有链的监控指标、告警规则、限流参数使用统一的数据模型
  - 链特定参数的合理默认值：基于出块时间和链 TPS 自动推算
- 生产级监控告警体系
  - 告警风暴抑制：相同告警在一定时间窗口内只发送一次
  - 告警升级：Warning 持续 N 分钟自动升级为 Critical
  - 自动恢复通知：异常恢复后发送恢复通知
  - 值班制度与告警路由：不同级别告警通知不同的人
- SRE 视角
  - SLI/SLO/SLA 的定义（如 Swap 成功率 > 99.5%，P99 延迟 < 3s）
  - 错误预算（Error Budget）：允许多少失败
  - 容量规划：根据历史数据预测资源需求
  - 混沌工程：主动注入故障验证系统韧性

## 自检问题

### L1 基础

1. 令牌桶算法中，如果桶容量为 20，填充速率为 10 个/秒，那么在桶满的情况下，前 2 秒最多能通过多少个请求？（提示：第 0 秒桶里有 20 个令牌）
2. Worker 池的 `sem chan struct{}` 容量设为 5，当前有 5 个 goroutine 正在执行任务。第 6 个任务提交时会发生什么？
3. 为什么监控指标用 `sync/atomic` 而不是 `sync.Mutex`？两者在性能上有什么差异？
4. 告警级别为什么要分为 Info/Warning/Critical？直接用一个级别行不行？

### L2 核心

5. 令牌桶的惰性填充（lazy refill）是如何工作的？相比使用定时器填充有什么优势？
6. `SwapQueue` 中的 `maxQueue` 参数如何影响系统行为？设置过大和过小分别会导致什么问题？
7. `ChainRuntime` 的 `GrayscaleMap` 如何实现灰度发布？如果灰度百分比为 30%，你会如何决定某个请求是否走灰度？
8. `MonitorService` 的检查间隔设为 10 秒。如果某条链在第 1 秒出现异常，最坏情况下要等多久才能收到告警？

### L3 进阶

9. 在多实例部署场景下（3 个实例），如果每个实例都使用容量 20、速率 10/s 的令牌桶，实际总 TPS 是多少？如何解决这个问题？
10. 假设 BSC 链的 RPC 节点突然全部超时，系统应该如何自动降级？需要触发哪些操作（限流调整、告警、DEX 禁用等）？
11. 配置热更新时，如果新配置有错误（如 MaxSwapTPS 设为负数），如何防止错误配置生效？
12. 告警风暴场景：某条链持续异常，每 10 秒产生一条告警。如何避免运维人员被告警淹没？

### L4 架构

13. 画出一笔 Swap 请求从进入系统到链上确认的完整路径，标注每一层的限流检查点和监控采集点。
14. 如果要新增对 Monad 链（高性能 EVM 链，TPS > 10000）的支持，需要调整哪些架构参数？限流策略是否需要根本性改变？
15. 系统的 SLO 定义为"Swap 成功率 > 99.5%，P99 延迟 < 3 秒"。当前月度错误预算还剩 20%，你会采取什么策略？
16. 你的系统同时运行 5 条链的 Swap 服务。某条链的 RPC 节点出现 50% 的超时率，但其他链正常。你如何确保故障链不影响其他链的正常服务？
